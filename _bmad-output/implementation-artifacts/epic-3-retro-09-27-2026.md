## Hallazgos

### Vista agregada: Delta de arquitectura

**AG-1 — Nueva capa de presentacion sin violaciones de capas** *(checked and clean)*
El epic introdujo tres archivos estaticos nuevos (`index.html`, `style.css`, `app.js`) y los monto en FastAPI via `StaticFiles`. La comunicacion entre el frontend y el backend ocurre exclusivamente a traves de `fetch()` a la API REST — no hay importaciones cruzadas entre `app/static/` y el codigo Python. El frontend no conoce modelos Pydantic; el backend no renderiza HTML. La separacion de capas declarada en `epic-3-context.md` (sec. Constraints, item 1) se sostiene en el diff.
*Fuente: diff `3a1501d^..cbfc0e7`, archivos `nuevamente/app/static/`, `nuevamente/app/main.py`.*

**AG-2 — `OCIStorageClient` crecio a 157 lineas con 4 metodos publicos** *(candidato a inspeccion; no god-class)*
Antes del epic la clase tenia 2 metodos (`upload_objeto`, `_build_client`). El epic agrego `list_objects` (Story 3.1) y `get_object` (Story 3.3), siguiendo exactamente el mismo patron: sin captura de excepciones, propagacion al llamante, log DEBUG con namespace/bucket/objeto. El crecimiento es lineal y coherente con el patron establecido.
*Fuente: diff `nuevamente/infra/oci.py`, +67 lineas neto.*

**AG-3 — `app.js` de 970 lineas concentra toda la logica de presentacion** *(observacion; ver AI-1 contexto)*
Un unico archivo JS maneja upload, validacion, polling, cinco renderers pedagogicos, historial e interactividad del Quiz. La spec declaro explicitamente "sin frameworks JS pesados" y el archivo esta organizado en secciones con funciones nombradas. A 970 lineas es el archivo mas grande del frontend y cualquier story adicional que extienda la UI lo incrementara. No es un defecto hoy, pero es el candidato mas obvio a fragmentacion si el epic 4 o 5 requieren mas logica de presentacion.
*Fuente: `wc -l nuevamente/app/static/app.js` = 970; diff `3a1501d^..cbfc0e7`.*

### Vista agregada: Mapa de duplicacion

**AG-4 — Patron de event delegation replicado dos veces** *(checked; duplicacion aceptada)*
`initQuizInteractivity()` (Story 3.2) e `initHistorialInteractivity()` (Story 3.3) siguen el mismo patron de event delegation sobre un contenedor estatico. El codigo es similar pero no identico — el primero maneja click+keydown sobre `.quiz-option` dentro de `#result-content`; el segundo maneja click+keydown sobre `.hist-item` dentro de `sidebarList`. No constituye duplicacion patologica en un MVP de este tamano.
*Fuente: diff `app.js`, funciones `initQuizInteractivity` y `initHistorialInteractivity`.*

**AG-5 — `StorageService` best-effort para `list_paquetes` y `get_paquete` con el mismo guard `_enabled`** *(checked and clean)*
Ambos metodos abren con `if not self._enabled: return []` / `return None` y capturan `Exception` en el bloque exterior. El patron es identico y consistente con el uso previo en `upload_documento_fuente_async` y `upload_paquete_async`. Sin divergencia.
*Fuente: diff `nuevamente/services/storage.py`, Story 3.1 y 3.3.*

### Vista agregada: Divergencia de patrones

**AG-6 — `assert self._client is not None` dentro de metodos sincronos** *(aceptado; no defecto)*
`list_paquetes()` y `get_paquete()` usan `assert self._client is not None` despues del guard `if not self._enabled`. La Story 3.1 Implementation Notes documenta explicitamente: "siempre True cuando `_enabled` es True". El assert es correcto y sirve como narrowing de tipo para el type checker, no como guard de runtime. El patron no estaba en la base de codigo anterior pero es coherente y correcto.
*Fuente: diff `nuevamente/services/storage.py` lineas 190 y 240.*

**AG-7 — `document_id` incluido en el dict de `list_paquetes` pero no documentado en la spec** *(divergencia menor; spec reconciliation propuesta)*
La spec de Story 3.1 (I/O Matrix, endpoint `GET /historial`) declara las claves `objeto_id`, `perfil`, `formato`, `fecha_epoch`, `fecha_iso`. La implementacion agrega `document_id` como clave extra. El campo es benigno (el frontend no lo usa hoy) pero diverge del contrato documentado.
*Fuente: `spec-3-1`, sec. I/O Matrix vs. diff `storage.py` linea 224.*

Cada renderer de Story 3.2 y la funcion `renderHistorial` de Story 3.3 aplican `escapeHtml()` sobre todo texto proveniente del servidor antes de inyectarlo en `innerHTML`. El Review Triage de Story 3.2 finding BH-1 verifico lineas 80-120 del diff explicitamente.

**RD-2 — Race condition: `stopPolling()` en `loadPaqueteFromHistorial`** *(corregido en Story 3.3)*
Finding BH-1 de Story 3.3 identifico que un polling activo sobreviviria al click en historial. El parche se aplico dentro de la misma story: `stopPolling()` es la primera linea de `loadPaqueteFromHistorial`.
*Fuente: `spec-3-3` Review Triage Log Finding BH-1; diff `app.js`.*

**RD-3 — `rsplit("_", 3)` fragil para valores de perfil/formato con underscore** *(diferido en Story 3.1; tracking abierto)*
Story 3.1 Finding BH-1 lo routeo como `low / defer` porque los enums actuales no contienen underscores. Si un valor futuro de `Perfil` o `FormatoPedagogico` incluyera underscore, el parsing de `list_paquetes` produciria metadata corrupta silenciosamente.
*Fuente: `spec-3-1` Review Triage Log Finding BH-1; diff `storage.py` funcion `list_paquetes`.*

**RD-4 — Doble-click concurrente en dos items del historial** *(diferido en Story 3.3)*
Story 3.3 Finding EC-4. Dos fetches paralelos por doble-click producen una race sobre la UI. El ultimo en resolver sobreescribe el area principal. Impacto cosmetico; no hay corrupcion de datos.
*Fuente: `spec-3-3` Review Triage Log Finding EC-4.*

**RD-5 — Ausencia de tests automatizados** *(patron pre-existente; diferido)*
Tres findings VG-1 (uno por story) confirman la ausencia de suite de tests. Los endpoints `GET /historial`, `GET /historial/{id}`, `list_paquetes()`, `get_paquete()`, `list_objects()`, `get_object()` no tienen tests. *Fuente: Review Triage Logs de specs 3.1, 3.2, 3.3.*
